# 전통적 스레드 모델의 문제점

> 공유 메모리 기반 동시성의 함정과 어려움

## 개요

전통적인 스레드 프로그래밍에서는 여러 스레드가 **공유 메모리**에 동시에 접근합니다. 이로 인해 다양한 동시성 문제가 발생합니다.

```
┌─────────────────────────────────────────────────────────────────┐
│                 Traditional Threading Model                      │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   Thread 1        Thread 2        Thread 3                      │
│      │               │               │                          │
│      │               │               │                          │
│      └───────────────┼───────────────┘                          │
│                      │                                          │
│                      ▼                                          │
│            ┌──────────────────┐                                 │
│            │   Shared Memory  │                                 │
│            │                  │                                 │
│            │  ⚠️ 동시 접근!  │                                 │
│            │                  │                                 │
│            └──────────────────┘                                 │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 1. Race Condition (경쟁 상태)

### 문제

여러 스레드가 동시에 같은 데이터를 읽고 쓸 때 결과가 예측 불가능해집니다.

```java
// 문제가 있는 코드
public class Counter {
    private int count = 0;

    public void increment() {
        count++;  // 원자적 연산이 아님!
    }
}
```

### 무슨 일이 일어나는가?

```
count++ 는 실제로 3단계 연산:
1. count 값 읽기 (READ)
2. 값 증가 (ADD)
3. 결과 저장 (WRITE)

┌─────────────────────────────────────────────────────────────────┐
│                    Race Condition Example                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   시간    Thread 1           count        Thread 2              │
│   ────    ────────           ─────        ────────              │
│                                                                  │
│   t0                          0                                 │
│   t1      READ count ──▶      0      ◀── READ count             │
│   t2      count = 0 + 1              count = 0 + 1              │
│   t3      WRITE ──────────▶   1                                 │
│   t4                          1      ◀── WRITE                  │
│                                                                  │
│   기대값: 2                                                      │
│   실제값: 1  ❌                                                  │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 실제 영향

```python
# 은행 계좌 예시
def transfer(from_account, to_account, amount):
    if from_account.balance >= amount:
        # 여기서 컨텍스트 스위치 발생 가능!
        from_account.balance -= amount
        to_account.balance += amount

# 두 스레드가 동시에 transfer 호출 시
# → 잔액이 음수가 되거나
# → 금액이 증발하거나 복제될 수 있음
```

## 2. Deadlock (교착 상태)

### 문제

두 개 이상의 스레드가 서로가 가진 자원을 기다리며 영원히 블록되는 상태.

```
┌─────────────────────────────────────────────────────────────────┐
│                        Deadlock                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   Thread 1                              Thread 2                │
│   ┌────────┐                           ┌────────┐               │
│   │        │──── Lock A 획득 ────────▶│        │               │
│   │        │                           │        │               │
│   │        │◀──── Lock B 획득 ────────│        │               │
│   │        │                           │        │               │
│   │        │──── Lock B 대기... ─────▶│        │               │
│   │   😵   │                           │   😵   │               │
│   │        │◀──── Lock A 대기... ─────│        │               │
│   └────────┘                           └────────┘               │
│                                                                  │
│   영원히 대기...                                                 │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 코드 예시

```java
// 데드락 발생 코드
Object lockA = new Object();
Object lockB = new Object();

// Thread 1
synchronized(lockA) {
    Thread.sleep(100);  // 시간 경과
    synchronized(lockB) {
        // 작업
    }
}

// Thread 2
synchronized(lockB) {
    Thread.sleep(100);  // 시간 경과
    synchronized(lockA) {
        // 작업
    }
}
```

### Deadlock 발생 조건 (4가지 모두 충족 시)

1. **Mutual Exclusion**: 자원은 한 번에 하나의 스레드만 사용
2. **Hold and Wait**: 자원을 가진 채 다른 자원 대기
3. **No Preemption**: 강제로 자원을 빼앗을 수 없음
4. **Circular Wait**: 순환 형태로 대기

## 3. Livelock

### 문제

Deadlock과 비슷하지만, 스레드들이 서로 양보하느라 진행이 안 되는 상태.

```
┌─────────────────────────────────────────────────────────────────┐
│                        Livelock                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   좁은 복도에서 마주친 두 사람:                                  │
│                                                                  │
│   Person A: "오른쪽으로 비켜야지" ──▶ 오른쪽 이동               │
│   Person B: "왼쪽으로 비켜야지"  ──▶ 왼쪽 이동 (충돌!)          │
│                                                                  │
│   Person A: "왼쪽으로 비켜야지" ──▶ 왼쪽 이동                   │
│   Person B: "오른쪽으로 비켜야지" ──▶ 오른쪽 이동 (또 충돌!)    │
│                                                                  │
│   ... 무한 반복 ...                                              │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 4. Starvation (기아 상태)

### 문제

특정 스레드가 자원을 영원히 얻지 못하는 상태.

```
┌─────────────────────────────────────────────────────────────────┐
│                       Starvation                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   우선순위 기반 스케줄링:                                        │
│                                                                  │
│   High Priority Thread 1  ──▶ [실행]                            │
│   High Priority Thread 2  ──▶ [실행]                            │
│   High Priority Thread 3  ──▶ [실행]                            │
│   Low Priority Thread     ──▶ [대기...대기...대기...😢]         │
│                                                                  │
│   낮은 우선순위 스레드는 영원히 실행 기회를 얻지 못함            │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 5. 복잡한 동기화 코드

### Lock 기반 코드의 문제점

```java
public class BankAccount {
    private final Object lock = new Object();
    private double balance;

    public void transfer(BankAccount to, double amount) {
        // 데드락 방지를 위한 순서 보장 필요
        Object firstLock = System.identityHashCode(this) <
                          System.identityHashCode(to) ? this.lock : to.lock;
        Object secondLock = firstLock == this.lock ? to.lock : this.lock;

        synchronized(firstLock) {
            synchronized(secondLock) {
                if (this.balance >= amount) {
                    this.balance -= amount;
                    to.balance += amount;
                }
            }
        }
    }
    // 😱 이 코드를 유지보수할 사람은?
}
```

### 복잡성 증가

```
┌─────────────────────────────────────────────────────────────────┐
│              Lock-based Code Complexity                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   기능 추가 시:                                                  │
│                                                                  │
│   1. 어떤 Lock을 잡아야 하는가?                                 │
│   2. Lock의 순서는 올바른가?                                    │
│   3. 기존 Lock과 충돌하지 않는가?                               │
│   4. Lock을 잡은 상태에서 다른 메서드 호출 시 안전한가?         │
│   5. 예외 발생 시 Lock이 해제되는가?                            │
│                                                                  │
│   → 모든 경우를 고려해야 하며, 실수하기 쉬움                    │
│   → 테스트로 발견하기도 어려움 (비결정적)                       │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 7. 성능 문제

### Lock Contention

```
┌─────────────────────────────────────────────────────────────────┐
│                    Lock Contention                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   많은 스레드가 같은 Lock을 경쟁할 때:                          │
│                                                                  │
│   Thread 1: [======실행======][    대기    ][ 실행 ]            │
│   Thread 2: [  대기  ][==실행==][   대기   ][실행]              │
│   Thread 3: [    대기    ][실행][대기][====실행====]            │
│   Thread 4: [      대기       ][=실행=][ 대기  ]                │
│                                                                  │
│   대부분의 시간을 대기에 소비                                    │
│   → 멀티코어의 이점 상실                                        │
│   → 단일 스레드보다 느려질 수도 있음                            │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### Context Switching 비용

```
스레드 컨텍스트 스위칭:
• 레지스터 저장/복원
• 캐시 미스 증가
• TLB 플러시
• 약 1-10 마이크로초 소요

1000개 스레드, 초당 1000번 스위칭
→ 1-10초/초가 컨텍스트 스위칭에 소비!
```

## Actor Model의 해결책

```
┌─────────────────────────────────────────────────────────────────┐
│            Thread Problems → Actor Solutions                     │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   문제                      Actor Model 해결책                   │
│   ─────                     ─────────────────                   │
│   Race Condition     →      상태 캡슐화, 순차 메시지 처리       │
│   Deadlock           →      Lock 없음, 메시지 기반 통신         │
│   복잡한 동기화      →      단순한 send/receive 모델           │
│   디버깅 어려움      →      메시지 로깅, 재현 가능성 증가       │
│   Lock Contention    →      Lock 없음, 경량 Actor              │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```
