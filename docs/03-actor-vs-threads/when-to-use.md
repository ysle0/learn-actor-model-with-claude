# 언제 Actor Model을 사용해야 하는가

> Actor Model이 적합한 상황과 부적합한 상황

## Actor Model이 적합한 경우

### 1. 대규모 동시 연결 처리

```
┌─────────────────────────────────────────────────────────────────┐
│              High Concurrency Scenarios                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   적합한 사례:                                                   │
│   • 채팅 서버 (수백만 동시 접속)                                │
│   • 게임 서버 (수만 동시 플레이어)                              │
│   • IoT 플랫폼 (수백만 디바이스)                                │
│   • WebSocket 서버 (장시간 연결 유지)                           │
│                                                                  │
│   ┌────────────────────────────────────────────┐                │
│   │  Connection 1 ──▶ [Actor 1]               │                │
│   │  Connection 2 ──▶ [Actor 2]               │                │
│   │  Connection 3 ──▶ [Actor 3]               │                │
│   │       ...                                  │                │
│   │  Connection N ──▶ [Actor N]               │                │
│   └────────────────────────────────────────────┘                │
│                                                                  │
│   각 연결이 경량 Actor로 표현되어 메모리 효율적                 │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 2. 상태가 있는 서비스

```
┌─────────────────────────────────────────────────────────────────┐
│              Stateful Services                                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   적합한 사례:                                                   │
│   • 사용자 세션 관리                                            │
│   • 게임 상태 관리                                              │
│   • 쇼핑 카트                                                   │
│   • 워크플로우 엔진                                             │
│                                                                  │
│   ┌─────────────────────────────────────────────┐               │
│   │           Player Actor                       │               │
│   │  ┌─────────────────────────────────────┐    │               │
│   │  │  State:                              │    │               │
│   │  │  • Position: (x, y, z)               │    │               │
│   │  │  • Health: 100                       │    │               │
│   │  │  • Inventory: [...]                  │    │               │
│   │  │  • Quest Progress: {...}             │    │               │
│   │  └─────────────────────────────────────┘    │               │
│   │                                              │               │
│   │  상태와 로직이 캡슐화되어 관리 용이          │               │
│   └─────────────────────────────────────────────┘               │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 3. 분산 시스템

```
적합한 사례:
• 마이크로서비스 통신
• 클러스터 간 메시지 전달
• 지리적으로 분산된 시스템
• Edge Computing

이유:
• 위치 투명성으로 로컬/원격 동일 코드
• 메시지 기반으로 네트워크 친화적
• 장애 격리 용이
```

### 4. 장애 허용 시스템

```
적합한 사례:
• 통신 시스템 (Ericsson)
• 금융 시스템
• 의료 시스템
• 24/7 서비스

Supervisor 계층 구조:
         [App Supervisor]
         /      |       \
   [Service]  [Service]  [Service]
      /  \       |         /  \
   [Worker]   [Worker]  [Worker]

장애 시 해당 부분만 재시작
```

### 5. 이벤트 기반 아키텍처

```
적합한 사례:
• 실시간 알림 시스템
• 스트리밍 데이터 처리
• CQRS/Event Sourcing
• Reactive 시스템

이벤트 흐름:
[Event Source] ──▶ [Actor A] ──▶ [Actor B] ──▶ [Actor C]
                      │
                      └──▶ [Actor D] ──▶ [Actor E]

비동기 이벤트 처리에 자연스러운 모델
```

## Actor Model이 부적합한 경우

### 1. 단순 CRUD 애플리케이션

```
┌─────────────────────────────────────────────────────────────────┐
│              Simple CRUD - Actor Overkill                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   일반적인 웹 API:                                               │
│                                                                  │
│   Request ──▶ Controller ──▶ Service ──▶ Repository ──▶ DB     │
│                                                                  │
│   이런 경우 Actor는 과도한 추상화:                               │
│   • 단순 요청-응답                                               │
│   • 상태 없음 (DB에 저장)                                       │
│   • 복잡한 동시성 요구 없음                                     │
│                                                                  │
│   → 전통적인 MVC/REST 패턴이 더 적합                            │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 2. CPU 집약적 계산

```
┌─────────────────────────────────────────────────────────────────┐
│              CPU-Intensive Computation                           │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   예시:                                                          │
│   • 영상 인코딩                                                  │
│   • 과학 계산                                                    │
│   • 머신러닝 학습                                               │
│   • 행렬 연산                                                    │
│                                                                  │
│   이런 경우:                                                     │
│   • 메시지 패싱 오버헤드 불필요                                 │
│   • 병렬 루프가 더 효율적                                       │
│   • GPU 활용 필요                                               │
│                                                                  │
│   → OpenMP, CUDA, 병렬 스트림 등이 더 적합                      │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 3. 강한 일관성 필요

```
┌─────────────────────────────────────────────────────────────────┐
│              Strong Consistency Required                         │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   Actor Model의 특성:                                            │
│   • 비동기 메시지 (최종 일관성)                                 │
│   • 메시지 순서는 발신자-수신자 쌍에서만 보장                   │
│                                                                  │
│   강한 일관성이 필요한 경우:                                     │
│   • 금융 거래 (원자적 이체)                                     │
│   • 재고 관리 (정확한 수량)                                     │
│   • 예약 시스템 (중복 방지)                                     │
│                                                                  │
│   해결책:                                                        │
│   • Saga 패턴 사용                                              │
│   • 또는 전통적 트랜잭션과 혼합                                 │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 4. 매우 낮은 레이턴시 요구

```
요구사항: < 1ms 레이턴시

Actor Model 오버헤드:
• 메시지 생성: ~수십 ns
• Mailbox enqueue: ~수백 ns
• 스케줄링: ~수십 ns
• 총: ~수 μs

극단적 저지연 시스템에서는:
• Lock-free 자료구조 직접 사용
• Busy-waiting
• Memory-mapped I/O
• DPDK, RDMA 등

→ HFT(High-Frequency Trading) 등에는 부적합
```

### 5. 단일 공유 자원

```
┌─────────────────────────────────────────────────────────────────┐
│              Single Shared Resource                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   모든 요청이 하나의 자원에 접근:                                │
│                                                                  │
│   Request 1 ──┐                                                 │
│   Request 2 ──┼──▶ [Single Actor] ──▶ 순차 처리                │
│   Request 3 ──┘                      (병목!)                    │
│                                                                  │
│   이런 경우 Actor가 병목:                                        │
│   • 모든 메시지가 한 Actor에 집중                               │
│   • 병렬 처리 불가                                              │
│                                                                  │
│   해결책:                                                        │
│   • Sharding으로 분산                                           │
│   • 또는 다른 동시성 모델 사용                                  │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

│       │                                                         │
│       ▼                                                         │
